# Project Direction and Open Design Arguments

> **Document role:** Owner-controlled decision workspace. This document records intent, observations, alternatives, and unresolved arguments. It is not an implementation claim and does not become an engineering mandate until the owner marks a decision **Accepted**.
>
> **Repository stage:** Version 0, pre-deployment. Phases 1–4 are historically delivered implementation milestones. Their completion does not imply that every underlying architectural assumption remains accepted or that the system is production-ready.
>
> **Current purpose:** Establish the desired system before rewriting Phase 5, `LEGAL.md`, or the implementation around assumptions made by prior agents.

## 1. How decisions are controlled

The earlier decision matrix was too conclusive. It mixed recommendations with owner decisions and collapsed several different questions into a single “keep/change” verdict. This document deliberately keeps them separate.

### 1.1 Two kinds of truth

No single file can be the absolute authority for both desired behavior and current behavior.

| Truth axis | Meaning | Authority order |
| --- | --- | --- |
| **Normative truth** | What the project should become and what constraints it chooses to impose | Owner decisions in this document → applicable external law/platform constraints → target `LEGAL.md`/architecture → `TODO.md` |
| **Descriptive truth** | What the repository demonstrably does now | Reproducible runtime observation → tests that exercise production paths → code/static inspection → operational documentation → planning claims |

When these axes disagree, the disagreement is not resolved by declaring one document “absolute.” It is recorded, researched, decided by the owner where necessary, and then implemented or documented.

### 1.2 Document responsibilities

| Artifact | Intended responsibility | Must not be used as |
| --- | --- | --- |
| `DIRECTION.md` | Owner intent, alternatives, open questions, accepted design decisions | Proof that a feature exists |
| `LEGAL.md` | Target operational covenants and legal posture for the projected post-v1.0 application, plus explicit implementation/conformance status | A false claim that version-0 code already enforces every covenant |
| `TODO.md` | Work decomposition, dependencies, acceptance criteria, and historical phase record | Current runtime truth or a second architecture book |
| `DISAGREEMENTS.md` | Evidence-backed conflict and defect registry | A parallel roadmap or permanent system specification |
| `docs/` | Explanations of accepted architecture, protocols, and operations | A place for speculative features presented as current behavior |
| `src/` | Current implementation | Automatic evidence that the implementation is intended or correct |
| `tests/` | Executable claims with stated scope and fixtures | Proof of properties the test never exercises |

### 1.3 Decision states

| State | Meaning |
| --- | --- |
| **Observed** | Directly supported by current code, tests, or a reproducible run |
| **Owner leaning** | Direction suggested by the owner's edits, but not yet precise enough to implement |
| **Proposed** | A technical recommendation for discussion, not an owner decision |
| **Research required** | Evidence is insufficient, unstable, legal, empirical, or platform-dependent |
| **Accepted** | Owner has selected the behavior and its important consequences |
| **Rejected** | Considered and explicitly excluded |
| **Deferred** | Valid question intentionally moved beyond the current milestone |

An accepted decision should eventually record: decision, rationale, rejected alternatives, affected invariants, implementation owner, validation method, and revisit trigger.

## 2. System intent versus current shape

### 2.1 Working product statement

**Owner leaning:** The product is a crawler that extracts metadata from selected platforms and discovers decentralized resources related to authoritative sources. Cosmetics are in scope. The system should favor packages for generic correctness and retain custom code for domain-specific policy.

This still leaves a material ambiguity: whether the primary product is a package registry, a broader VRChat asset index, a provenance graph, or all three exposed through separate projections. Phase 5 taxonomy, evidence, legal posture, and API design all depend on settling that boundary.

### 2.2 Current pipeline model

```text
Seed or lead
  → discovery candidate
  → access-policy decision
  → fetch
  → parse/extract
  → normalize
  → observation/snapshot storage
  → evidence linkage
  → canonical projection
  → export/API/edge sync
  → downstream consumer
             ↘ reports/steering/opt-out ↗
```

The implementation currently contains most of these behaviors, but their boundaries are blurred. Platform adapters perform transport policy, HTML parsing, normalization, filtering, persistence, graph expansion, and rate-limit accounting in different combinations.

## 5. Data, identity, and provenance arguments

### 5.1 Observation and projection context

An **observation** is a time-stamped claim obtained from a source: “source S reported field F as value V at time T.” A **projection** is the current catalog interpretation synthesized from one or more observations: “the catalog currently presents package P with these fields.”

Projections are expected to change when new observations, classification rules, overrides, or delisting policy change. They should be reproducible from retained evidence and policy versions. Manual overrides and legal tombstones should not disappear when a projection is rebuilt.

The current `entities` table does not actually provide an immutable observation history. Its primary key is the stable entity ID, and `saveEntity()` uses `INSERT OR REPLACE`, so a later crawl overwrites the earlier row while preserving only `created_at`. It is a latest-source snapshot table despite being labeled an “Immutable Observation Lake.”

### 8.1 Dependency acceptance gate

A dependency should be adopted only when all applicable checks pass:

1. It solves generic infrastructure rather than hiding project policy.
2. Its license is compatible with the project and intended distribution.
3. It is maintained or sufficiently stable for its narrow purpose.
4. It works in Bun development, tests, and compiled binaries on intended platforms.
5. It materially improves correctness, conformance, security, or maintained code volume.
6. Its failure modes and upgrade surface are understood.
7. It is wrapped at a project boundary when replacement or policy isolation is valuable.
8. Fixtures or conformance tests demonstrate equivalence before custom code is removed.
9. Documentation identifies why it exists and the subset of its API the project relies on.
