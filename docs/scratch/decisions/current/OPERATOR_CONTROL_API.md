# Operator control API and hybrid lead review

**Owner decision (2026-09-28):** A discovered lead matching a reviewed source rule can become a coordinator job automatically. Unknown hosts, paths, or lead kinds stay pending for review. A node still needs a coordinator lease before fetching. Selecting every available capability is not blanket authorization. The later eighth Shopify capability is lead-only and has no auto-queue rule.

The control API is separate from `/v1/node/*`. The local coordinator binds to `127.0.0.1`. It accepts operator requests only when `COORDINATOR_OPERATOR_TOKEN` is configured as a 64-character hex token generated from 32 random bytes. Node credentials do not authorize operator routes. The token is never passed to standalone nodes by the local smoke. A future dashboard can call this versioned API through a same-origin Worker or adjacent control application. No dashboard, account system, remote TLS, or Cloudflare deployment exists yet.

The operator handler reuses the bounded JSON request reader. It validates the same request whether called in-process or through loopback HTTP. Both node and operator handlers pass browser-target builds. But neither is a deployed Worker application yet. The compiled smoke verifies that the operator token works and a node token fails. `operator_actions` records manual lead decisions. `operator_rule_actions` records rule creation, disablement, and failed automatic promotions. `node_credential_actions` records API issuance without token material. The CLI remains an explicit local control path. It is not a substitute for the future dashboard identity and authorization model. The API route is **operator-initiated issuance**, not open node self-registration. Unknown nodes cannot get credentials from `/v1/node/*`. The owner decision on remote registration trust remains deferred as TOPOLOGY-02.

The `leads [status] [limit] [cursor]` CLI uses keyset pagination and prints `{leads,nextCursor}`. A cursor is opaque, bounded, validated, and tied to the selected status. Malformed or cross-status cursors fail. This avoids hiding leads beyond the first 100. But it is not a frozen snapshot: newly discovered or reclassified leads can appear or disappear while an operator pages through a changing status set.

The auto-queue-rule list also uses a bounded, opaque keyset cursor and returns `{rules,nextCursor}`. Rules created while paging can change what a later page contains. Neither list is a frozen snapshot.

**Source-profile boundary is local and partial.** Both manual and auto-queued jobs need a matching active profile before automatic or explicit robots refresh or a node lease. The lease binds the profile ID. Fetching heartbeats and new submissions recheck it, and the profile delay raises origin pacing. The field `retainClasses` reaches the node through the versioned job payload. Unapproved creator prose is stripped and independently rejected if submitted. New evidence records the profile ID. This does not approve any source, enforce publication classes in a public catalog, cover legacy direct drivers, or supply a complete delisting workflow. The profile list returns `{profiles,nextCursor}`. See [source access and safety](SOURCE_ACCESS_AND_SAFETY.md).

The initial profile manager rejects overlapping active path scopes for the same platform, origin, and purpose. This avoids silent fallback to a broader grant when a narrow grant is disabled. A later revision workflow can explicitly replace or narrow a profile with a reviewed transition. None is implemented yet.

An exact path rule such as `/index.json` matches only that path with no query. A scope ending in `/` matches paths in that directory. Rules are initially limited to `vpm_listing`. Repository and ZIP leads stay pending. Disabling or expiring a rule stops its future and in-flight fetch authority. **It does not erase existing evidence or retroactively cancel separately seeded jobs.** That broader source-access stop remains an open gate. Existing pending leads are not auto-reconciled when a new rule is created. Operators can review them individually until a bounded reconciliation action exists.

Source-access profiles are separate from auto-queue rules. Their optional `exactQuery` is an ASCII `key=value` sequence (for example `page=1`) attached to one exact `pathScope`. It never acts as a wildcard or extends a directory grant. A canonical percent-encoded UTF-8 path can be reviewed as an exact path. Encoded ASCII and encoded directory scopes are rejected. Existing profiles without `exactQuery` continue to match only query-free targets. Creating a profile is an operator review action, not evidence that a source permits crawling.

The node result schema accepts `creator_profile`, `publisher_site`, and `storefront_product` discovery leads. These can optionally be anchored to a `discoveredFromItemKey` on a multi-item source page. The operator list exposes that anchor as `discovered_from_item_key`. Older leads have `null`. These kinds remain pending and cannot be approved as VPM jobs or matched by VPM-only auto-queue rules. Recording the anchor does not authorize following the link, nor does it establish author ownership or product equivalence.

A reviewed auto-queue rule must not be reduced to `robots.txt` permission or presented as a full legal profile. A full profile needs allowed endpoints, methods, discovery roles, retained and publishable fields, rate floors, stop conditions, review evidence, actors, revisions, and expiry. A newly found URL is a lead, not accepted catalog fact. Neither a node nor a dashboard can bypass coordinator lease and policy checks.
