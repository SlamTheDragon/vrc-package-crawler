# Source-access gate: decision and implementation design

Status: **owner chose separate source-access profiles; local coordinator gate partially implemented** (2026-09-28). This document does not approve a source, select a capability, or authorize a live fetch. It describes the gate between a queued job and a network request. An eighth, lead-only Shopify capability was added separately after the original seven-capability baseline; the same profile gate applies to it. This is an engineering control proposal, not legal advice; a source-specific review still has to determine its usable endpoints and retained/published representations. The source-by-source evidence remains in [SOURCE_ACCESS_REVIEW.md](SOURCE_ACCESS_REVIEW.md).

The shared DTO and exact-origin/path/purpose matcher live in `src-crawler/src/shared/source_access_profile.ts`. The local SQLite store has zero default grants and authenticated, audited create/list/disable routes. Automatic and explicit robots refresh now require a due job matching an active profile; claim binds that profile to the lease and applies its rate floor; fetching heartbeat and new result submission recheck the bound profile. Disable clears its active leases. The node receives retained classes and omits unapproved creator prose; the coordinator independently rejects unauthorized prose or normalized evidence. New versions/events/issues/leads record the approving profile ID. Offline fixtures and compiled local smokes cover the narrow boundary. This is **not full source-policy conformance**: source-specific approval/retention research, older DB migration/recovery proof, transitional version-0 direct driver paths, full objection/delisting, and public publication filters remain open.

## The owner decision and considered alternatives

**Owner decision:** every job, manual and auto-queued, must match a separate, active, scoped source-access profile before a live fetch lease. A seed queues a request; it is not approval. A matching auto-queue rule permits lead-to-job promotion, not network access. The local coordinator enforces the fetch side of that boundary; evidence/publication policy and transitional version-0 paths are not complete.

| Position | What it would mean technically | Advantage | Failure mode unless constrained | Owner status |
| --- | --- | --- | --- | --- |
| A. Structured seed is approval | Replace the bare `seed <platform> <url>` action with an auditable, expiring per-URL approval record containing reviewed request and retention/publication scope. Repeat fetches remain bounded by that record. Auto-queued jobs still need an equivalent reviewed source authorization, not merely an auto-queue rule. | Smallest approval scope; deliberate one-off metadata smokes remain easy to explain. | A bare seed, a CLI history entry, or a URL alone cannot express allowed methods, cadence, retention, publication, expiry or revocation. Treating the current bare seed as approval would preserve the gap. Many seeds could become an unreviewable policy inventory. | **Not chosen for this milestone** |
| B. Separate source profile for both routes | Operator creates/reviews a profile scoped to platform, canonical origin, exact/path-prefix endpoint and purpose; manual and auto-queued jobs match it before refresh/claim. A job still needs fresh robots, pacing and a node lease. | One auditable policy can cover repeated jobs and both promotion paths; revocation has source-wide semantics. | A broad profile could over-authorize if path, query, method, representation, expiry or host matching is loose. The profile's existence is a documented operator judgment, not a legal finding. | **Chosen; local fetch gate implemented, broader policy incomplete** |
| C. Bare seed/auto-queue rule is approval | Keep current behavior and treat job/rule creation as sufficient. | No implementation cost. | Current records omit the terms/endpoint and field-level retention decision; manual and auto jobs have inconsistent stop scopes. This does not meet the stated G3/G5 source-profile gate. | **Not recommended; not an accepted owner decision** |

The decided boundary is **approval granularity**, not whether robots should be honored, whether seven drivers are selected, or whether hybrid lead review applies. A seed is a request to queue work, not an approval. This does not make a community-directory lead authoritative product evidence.

## Current implementation versus intended boundary

| Boundary | Current evidence | Gap / target invariant |
| --- | --- | --- |
| Job creation | `seed` queues a validated URL with explicit/default purpose; VPM auto-promotion still requires a VPM-only rule and queues a `discovery` job. Neither path creates a source profile. | Add broader typed lead mappings and policy lineage; do not let a selected capability or job imply approval. |
| Robots preflight | Both automatic and explicit refresh require a due job matching an active profile. `serve` runs the bounded refresh batch on startup and each minute. Refresh reservation checks the origin's active job and pacing floor, holds a cross-process refresh lease, and advances the same origin floor by the stricter profile delay. A profile disable invalidates a refresh lease when no other approved due job remains. | Owner may still choose a separate, tightly budgeted unapproved robots preflight; until then, require profile. A cross-process in-flight robots socket can finish within its transport timeout, but a revoked completion is discarded. Other support-origin traffic is not yet unified under this floor. |
| Claim | Within the SQLite transaction, a job needs fresh exact-URL robots allowance, capability, origin pacing, no active same-origin robots refresh, active auto-queue rule when applicable, and an exact matching active source profile. The profile ID binds to the lease; its delay raises the origin floor. | Exact ASCII queries and canonical UTF-8 paths have narrow offline tests; review any broader query/encoding policy separately and verify lookup performance under large job inventories. |
| During fetch | Fetching heartbeats recheck the exact bound profile and rule; the standalone node aborts metadata egress on a failed heartbeat. Transport pins public DNS, enforces HTTPS GET/2 MB and rejects redirects. | Document bounded, not instantaneous, cancellation; extend the same boundary to transitional version-0 direct drivers and test live socket cancellation. |
| Submission | Before new evidence is committed, `submit` rechecks the bound profile, lease, rule and robots in one transaction. It rejects unapproved normalized evidence or creator prose. New evidence rows record the profile ID. Duplicate accepted results remain idempotent. | Add profile-aware public projection and explicit retention duration/removal; test duplicate replay after revocation and migration of pre-policy evidence. |
| Revocation | Disabling a profile atomically invalidates its active job leases and stops later claim/heartbeat/new submission; auto-queue rule disable, URL suppression and node revoke retain separate scopes. | Add objection/source-wide stop semantics, historical evidence treatment, public tombstones and creator-wide delisting. |
| Retention/publication | The lease carries approved retain classes; the node strips unapproved summaries and the coordinator independently rejects submitted prose or normalized evidence outside that scope. `source_versions.payload_json` is a normalized observation payload, not raw HTTP body. There is no accepted coordinator-to-public catalog bridge yet. | Define source-specific retain durations and publish classes; gate all export/sync routes and avoid assuming that a fetch approval permits public prose or media. |

The [Robots Exclusion Protocol](https://www.rfc-editor.org/rfc/rfc9309.html#section-1) explicitly says its rules are not access authorization. Its handling of unavailable and unreachable robots results is defined in [Â§2.3.1](https://www.rfc-editor.org/rfc/rfc9309.html#section-2.3.1); the gate above is an additional project policy, not a reinterpretation of robots. A later Cloudflare Queues transport, if selected, has [at-least-once delivery](https://developers.cloudflare.com/queues/reference/delivery-guarantees/); therefore any queue delivery still needs coordinator-side idempotency and policy re-evaluation at claim/submit. No Queue product is required for the local design.

## Candidate policy object and evaluation

The current schema has a stable `profile_id`, platform, exact canonical origin, exact or slash-terminated path, optional exact ASCII query, fixed GET, purpose (`discovery`/`metadata`), expiry, delay floor, review reference/reason, retain/publish class arrays, creation/disable timestamps and audit actor. Canonical percent-encoded UTF-8 paths are allowed only as exact scopes; encoded ASCII and encoded directory scopes are rejected. This conservative distinction is informed by the [WHATWG URL Standard's path and percent-encoding rules](https://url.spec.whatwg.org/), but cannot establish how any remote server normalizes URLs internally; a source-specific review still has to check that. It does **not** yet model immutable revisions, source role, review evidence digest, general query policy, request budget or retention duration. The table below is the broader target, not a claim about implemented fields:

| Field | Purpose / guard |
| --- | --- |
| `profile_id`, immutable `revision`, `state` (`draft`, `active`, `disabled`, `expired`), `created_at`, `expires_at`, `disabled_at` | Stable audit identity. Updates create revisions; no in-place silent widening. Active validity uses coordinator time. |
| `platform`, `source_role` (`first_party_product`, `first_party_metadata`, `discovery_only`, etc.), canonical `https` `origin` | Prevent a community index, VPM listing host, GitHub API and seller storefront from inheriting one another's approval. Role is explicit; origin equality is exact. |
| `path_scope` (exact or slash-terminated prefix), `allowed_methods` (currently `GET`), explicit query policy and endpoint class | Match the actual network target, not just a host. Reject path normalization ambiguities, credential-bearing URLs, ports, fragments and noncanonical encodings. A prefix must respect directory boundaries. Query-bearing URLs require an explicit rule. |
| `purpose`, `review_reference`, `reviewed_at`, `reviewer`, `reason`, `evidence_digest_or_link` | Show which endpoint/terms/rate assessment an operator relied on. A review reference is evidence provenance, not proof of permission. |
| `min_delay_ms`, concurrency/budget, retry/objection/challenge stop conditions | Combine with origin-wide pacing by taking the stricter effective floor. A `429`, challenge or objection must not be retried simply because the profile remains active. |
| `accept_classes`, `retain_classes`, `publish_classes`, `retention_until_or_policy_id` | Distinguish transient response, normalized facts, creator prose, raw JSON, URL, image derivative, historical versions and public projection. Absence is deny, not â€œretain everything.â€ Version these decisions independently of fetch approval if necessary. |

Evaluator input is `(platform, GET, canonical URL, purpose, now, active profile, suppression/objection state, robots snapshot, origin pace)`. A job may be **queued** before access approval, but a **claim** is granted only when each required predicate is satisfied. The lease binds a profile ID and new evidence records it. Active profiles with overlapping platform/origin/purpose paths are rejected for now, avoiding implicit fallback to a broader profile after disable; a later revision model must preserve that invariant. A deny/stop record should override all allows.

One source profile should not be made synonymous with a VPM `lead_autoqueue_rules` row. That rule answers â€œmay this lead become a job without another human click?â€; the access profile answers â€œmay this job cause this network request, and what may be retained/published?â€ Both can expire or be disabled independently. Unknown lead kinds and destinations remain pending review regardless of a permissive host profile until a typed lead-to-job mapping exists.

## Transition plan for the accepted separate-profile boundary

1. **Partly done:** strict operator payload and authenticated create/list/disable routes plus local CLI exist. Add inspect/revision workflow, reviewer identity beyond one token, evidence digest/link verification and durable amendment history. Node credentials never administer profiles.
2. **Partly done:** SQLite profile tables, nullable old-job `lease_profile_id`, purpose and evidence profile IDs exist with zero synthesized grants. An older-schema fixture proves pre-policy leases are cleared on upgrade and unbound leases cannot continue or submit; define backup/rollback for an actual local DB upgrade. The prototype `bin/crawler_state.db` remains read-only test evidence, not an approval migration.
3. **Partly done:** one exact URL matcher is reused for refresh eligibility, claim and bound lease checks; robots, claim, heartbeat and submit each recheck their relevant predicates. Preserve strict transport URL/DNS controls. The exact-query/canonical UTF-8 path extension has offline BOOTH browse fixtures. The lease now carries purpose; the BOOTH node adapter extracts bounded candidate leads from the reviewed-shape category path, and the coordinator rejects a browse job's product observations and off-site leads. This is exercised over loopback with synthetic HTML, not a live BOOTH approval or fetch. General query policy remains open.
4. Keep discovery reports as provenance-bearing pending leads. A source-approved discovery index may be fetched only within its reviewed role; its credited author or outbound seller link does not transfer authorization to the destination. Approving a lead to become a job and approving its destination access are separate actions.
5. **Partly done:** normalized facts and creator prose are checked at submission; the node minimizes prose according to the lease. Add profile-aware publication projector and retention duration/removal; if policy changes later, recompute/suppress public projection without silently rewriting observations. Decide pre-policy historical rows before export, including tombstone propagation and takedown.
6. The opt-in live smoke scripts require an explicit review reference and retained-class selection, create short-lived exact-path profiles, and retain no public classes. The revised GitHub and two-origin VPM template smokes both passed through the gate on 2026-09-28. After robots preflight joined the origin pacing floor, one-time reviewed regression retests passed again, including stored profile/prose assertions for both. Keep the default seven *capabilities* selected while unapproved sources have zero eligible fetch leases.

## Acceptance scenarios and coverage still required

Offline tests now exercise portions of GATE-01/03/05/08/10/11: unapproved manual and auto-queued jobs receive no lease, profile disable invalidates active authority, duplicate accepted result replay remains idempotent, an older DB gains no grants, and operator profile management rejects node credentials. The pure matcher fixtures cover parts of GATE-02, and the multi-process smoke still tests origin leases. **No scenario below should be read as fully discharged** until its whole assertion set, especially sustained/live and publication behavior, is verified.

| ID | Test scenario and required assertion |
| --- | --- |
| GATE-01 | With all selectable capabilities and an unapproved manual seed queued, automatic robots refresh follows the chosen documented preflight rule; **claim is empty** and zero product requests are made. An unapproved auto-queued job behaves identically. |
| GATE-02 | A valid exact-scope approval permits only the matching canonical URL/method/platform/purpose after fresh robots allow and origin pacing. Adjacent path (`/item2` vs `/item`), unapproved query, subdomain, redirected host, wrong method and wrong platform fail. An explicit exact-query profile may allow that one query; directory scopes respect slash boundaries and never include encoded children. |
| GATE-03 | A VPM lead matching an auto-queue rule but lacking source approval may become a queued job if chosen by design, yet never receives a lease. A source-approved but rule-unmatched lead remains pending review. Manually approved leads still need source approval under option B. |
| GATE-04 | Missing, stale, disallowing or unreachable robots never yields a lease, even with active source approval. A 404/410 robots result follows the RFC-specific missing-file behavior but cannot bypass source approval. Refresh requests obey the chosen preflight policy. |
| GATE-05 | Disable, expiry, source objection or scope narrowing atomically prevents new claims and rejects an in-flight fetching heartbeat and new result submission. The node's periodic heartbeat aborts egress within its documented interval; test an injected blocked fetch. Distinguish this from an instantaneous network-wide cancellation claim. |
| GATE-06 | Node credential revoke, URL suppression and auto-queue-rule disable retain their own scopes. Source approval disable stops both manual and rule-backed jobs matching that source; a neighboring approved source remains operable. |
| GATE-07 | Two coordinator processes racing to claim or refresh the same origin cannot exceed the origin lease/budget. Revoke during claim/submit uses SQLite transaction boundaries; no post-revocation new evidence is committed. |
| GATE-08 | A duplicate identical submission returns the recorded idempotent result without another version/event, including after later policy disable; a changed body/key for the same lease is rejected. The audit distinguishes â€œpreviously acceptedâ€ from â€œcurrently authorized.â€ |
| GATE-09 | A response with normalized facts, raw payload, creator prose and image derivative is retained only for explicitly allowed classes. Public export includes only publishable classes; unknown class is withheld. Revocation/public suppression does not silently imply either historical deletion or continued publication. |
| GATE-10 | Migration from an old local coordinator DB with seeded `source_rule_id NULL` jobs and rule-backed jobs creates **zero** active approvals. No existing job can claim after upgrade without deliberate review. No prototype DB data is silently imported. |
| GATE-11 | Operator route rejects absent/node/invalid token, malformed or wrong-version JSON, broad/ambiguous scope, expired approval and an attempted silent widening. An audit event exists for every approval/disable action. In-process and loopback HTTP validation agree. |
| GATE-12 | A small opt-in live test for one specifically reviewed endpoint records origin, exact URL, effective approval revision, robots snapshot ID, lease ID, retained classes and request count. It verifies no binary download, unexpected redirects or unapproved outbound leads. No fixture-only test is labeled proof of live compliance. |

The existing `src-crawler/src/tests/local_coordinator_protocol.test.ts`, `src-crawler/src/tests/operator_control_api.test.ts`, `src-crawler/src/tests/robots_refresh_service.test.ts`, `src-crawler/src/tests/node_lease_runner.test.ts` and live smoke scripts are natural test locations, but their current green status does **not** prove GATE-01â€“12.
