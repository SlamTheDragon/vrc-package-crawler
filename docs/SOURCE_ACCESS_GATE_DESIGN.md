# Source-access gate: decision and implementation design

Status: **design only; owner decision pending** (2026-09-28). This document does not approve a source, alter the seven selected node capabilities, or authorize a live fetch. It describes the missing gate between a queued job and a network request. It is an engineering control proposal, not legal advice; a source-specific review still has to determine its usable endpoints and retained/published representations. The source-by-source evidence remains in [SOURCE_ACCESS_REVIEW.md](SOURCE_ACCESS_REVIEW.md).

## The decision the owner must make

**Does an operator's `seed` action itself constitute a scoped source-access approval, or must *every* job, manual and auto-queued, match a separate, active source-access profile before a live fetch lease?**

| Position | What it would mean technically | Advantage | Failure mode unless constrained | Owner status |
| --- | --- | --- | --- | --- |
| A. Structured seed is approval | Replace the bare `seed <platform> <url>` action with an auditable, expiring per-URL approval record containing reviewed request and retention/publication scope. Repeat fetches remain bounded by that record. Auto-queued jobs still need an equivalent reviewed source authorization, not merely an auto-queue rule. | Smallest approval scope; deliberate one-off metadata smokes remain easy to explain. | A bare seed, a CLI history entry, or a URL alone cannot express allowed methods, cadence, retention, publication, expiry or revocation. Treating the current bare seed as approval would preserve the gap. Many seeds could become an unreviewable policy inventory. | **Open** |
| B. Separate source profile for both routes (recommended) | Operator creates/reviews an immutable-revision profile scoped to platform, canonical origin and exact/path-prefix endpoint, then manual seeds and auto-queued jobs reference or match it. A job still needs fresh robots, pacing and a node lease. | One auditable policy can cover repeated jobs and both promotion paths; revocation has source-wide semantics. | A broad profile could over-authorize if path, query, method, representation, expiry or host matching is loose. The profile's existence is a documented operator judgment, not a legal finding. | **Open; recommendation only** |
| C. Bare seed/auto-queue rule is approval | Keep current behavior and treat job/rule creation as sufficient. | No implementation cost. | Current records omit the terms/endpoint and field-level retention decision; manual and auto jobs have inconsistent stop scopes. This does not meet the stated G3/G5 source-profile gate. | **Not recommended; not an accepted owner decision** |

The narrow decision is **approval granularity**, not whether robots should be honored, whether seven drivers are selected, or whether hybrid lead review applies. If the owner chooses A, implement a first-class per-URL approval object and the same runtime checks below; do not keep the unstructured seed as an implicit grant. If the owner chooses B, a seed is a request to queue work, not an approval. Neither choice makes a community-directory lead authoritative product evidence.

## Current implementation versus intended boundary

| Boundary | Current evidence | Gap / target invariant |
| --- | --- | --- |
| Job creation | `src/worker/local_main.ts` exposes bare `seed`; `LocalCoordinatorStore.seedJob` validates HTTPS/public target, known itch `/search` exclusion and GitHub endpoint, then inserts a pending job. Auto-promotion applies a VPM-only `lead_autoqueue_rules` match. | Record the policy basis separately from the fact that a URL entered the queue. No node-created job. Auto-queue eligibility and source access are independent predicates. |
| Robots preflight | `claimDueRobotsRefresh` selects due jobs even when `source_rule_id IS NULL`; `serve` runs the refresh batch on startup and every minute. Explicit `refresh-robots` can target an origin independently. | Decide whether `robots.txt` is allowed as a narrowly classified preflight before source approval, or only after approval. Either way, never schedule arbitrary robots requests from an unapproved queued URL by accident. Record the reason, target origin and request budget. Explicit refresh must use the same reviewed-scope rule or a documented preflight exception. |
| Claim | `claim` requires a fresh per-origin robots snapshot, exact-URL robots allowance, node capability and origin pacing. A rule-backed job requires an active auto-queue rule; a manual job with `source_rule_id NULL` passes that condition. | Check active source approval for the **actual URL, method, platform and job purpose** inside the same SQLite transaction that claims the job. No broad host substring match or cross-origin inheritance. Return no lease when unavailable. |
| During fetch | `runLeasedJob` heartbeats before and during egress, aborting on heartbeat failure; `fetchPublicMetadata` pins public DNS, enforces HTTPS GET/2 MB and never follows redirects. `heartbeat` currently checks the rule only if a rule ID exists. | Check the approval revision/state on every fetching heartbeat, including manual jobs. A revoked/expired profile must invalidate subsequent heartbeat checks and stop the node within the heartbeat/polling bound; no claim of instantaneous socket cancellation. A node must not follow an unapproved discovered URL or redirect. |
| Submission | `submit` checks live node credential, lease, active auto-queue rule if present, and current robots; duplicate lease/result is idempotent. It writes observations, versions, events, leads and issues. | Recheck approval and policy revision **before any new evidence is committed**, in the same transaction. Define duplicate replay semantics: a previously accepted identical result may return its recorded response without re-ingestion, but must not create new publication or conceal a later revocation. A result arriving after revocation must not create new evidence. |
| Revocation | Disabling a VPM auto-queue rule clears rule-backed leases. `suppressUrl` blocks one exact job. Separately seeded jobs remain independent. Node revocation invalidates node credentials. | Add source-scope disable/expire/objection stop. Atomically prevent future claims, invalidate matching active leases, and make heartbeats/submissions fail. Preserve audit records. Treat historical evidence, public projection and downstream tombstones as **separate** decisions; revocation alone need not silently delete evidence. |
| Retention/publication | `source_versions.payload_json` retains submitted payloads. The rule and seed schemas have no representation-specific retention or publication fields. | Gate *what is accepted into evidence* and *what is exported* separately. An access grant is not permission to publish raw descriptions, images or historical payloads. Unknown retention class should not silently default to permanent archive or public export. |

The [Robots Exclusion Protocol](https://www.rfc-editor.org/rfc/rfc9309.html#section-1) explicitly says its rules are not access authorization. Its handling of unavailable and unreachable robots results is defined in [§2.3.1](https://www.rfc-editor.org/rfc/rfc9309.html#section-2.3.1); the gate above is an additional project policy, not a reinterpretation of robots. A later Cloudflare Queues transport, if selected, has [at-least-once delivery](https://developers.cloudflare.com/queues/reference/delivery-guarantees/); therefore any queue delivery still needs coordinator-side idempotency and policy re-evaluation at claim/submit. No Queue product is required for the local design.

## Candidate policy object and evaluation

This is the minimum **proposed** shape for option B, not an accepted schema:

| Field | Purpose / guard |
| --- | --- |
| `profile_id`, immutable `revision`, `state` (`draft`, `active`, `disabled`, `expired`), `created_at`, `expires_at`, `disabled_at` | Stable audit identity. Updates create revisions; no in-place silent widening. Active validity uses coordinator time. |
| `platform`, `source_role` (`first_party_product`, `first_party_metadata`, `discovery_only`, etc.), canonical `https` `origin` | Prevent a community index, VPM listing host, GitHub API and seller storefront from inheriting one another's approval. Role is explicit; origin equality is exact. |
| `path_scope` (exact or slash-terminated prefix), `allowed_methods` (currently `GET`), explicit query policy and endpoint class | Match the actual network target, not just a host. Reject path normalization ambiguities, credential-bearing URLs, ports, fragments and noncanonical encodings. A prefix must respect directory boundaries. Query-bearing URLs require an explicit rule. |
| `purpose`, `review_reference`, `reviewed_at`, `reviewer`, `reason`, `evidence_digest_or_link` | Show which endpoint/terms/rate assessment an operator relied on. A review reference is evidence provenance, not proof of permission. |
| `min_delay_ms`, concurrency/budget, retry/objection/challenge stop conditions | Combine with origin-wide pacing by taking the stricter effective floor. A `429`, challenge or objection must not be retried simply because the profile remains active. |
| `accept_classes`, `retain_classes`, `publish_classes`, `retention_until_or_policy_id` | Distinguish transient response, normalized facts, creator prose, raw JSON, URL, image derivative, historical versions and public projection. Absence is deny, not “retain everything.” Version these decisions independently of fetch approval if necessary. |

Candidate evaluator input is `(platform, method, canonical URL, purpose, now, active profile revision, suppression/objection state, robots snapshot, origin pace)`. A job may be **queued** before access approval, but a **claim** is granted only when each required predicate is satisfied. The match result should record a policy revision on the lease/job; do not rely solely on looking up a mutable rule ID later. When multiple profiles overlap, choose the narrowest deterministic match and never union permissions from several profiles. A deny/stop record overrides all allows. For option A, the evaluator is identical but receives a per-URL approval record rather than an origin/path profile.

One source profile should not be made synonymous with a VPM `lead_autoqueue_rules` row. That rule answers “may this lead become a job without another human click?”; the access profile answers “may this job cause this network request, and what may be retained/published?” Both can expire or be disabled independently. Unknown lead kinds and destinations remain pending review regardless of a permissive host profile until a typed lead-to-job mapping exists.

## Transition plan after the owner chooses A or B

1. Add a versioned, strict operator payload and authenticated routes/CLI for create, list, disable and inspect of approval objects. Use the separate operator token; node credentials must never administer approvals. Record actor, rationale, source evidence and every revision/disable action. Keep source-policy DTOs independent of node job DTOs.
2. Add SQLite approval tables and a `policy_revision_id` (nullable during migration) to jobs/leases and evidence provenance. Start the fresh pre-production DB with **no active approvals**. For an existing local coordinator DB, add nullable columns/tables without synthesizing grants. Existing pending, leased and done jobs must be denied new claims until explicitly reviewed; cancel or invalidate old leases on upgrade. The prototype `bin/crawler_state.db` is read-only test evidence, not an automatic approval migration. Back up the local DB before the production migration.
3. Refactor a single URL policy evaluator used by manual seed validation or eligibility, auto-promotion, queued robots scheduling, claim, fetching heartbeat and submit. Each operation still checks its own relevant predicates; one early check cannot substitute for later expiry/revocation checks. Preserve the strict transport URL/DNS gate independently.
4. Keep discovery reports as provenance-bearing pending leads. A source-approved discovery index may be fetched only within its reviewed role; its credited author or outbound seller link does not transfer authorization to the destination. Approving a lead to become a job and approving its destination access are separate actions.
5. Add an evidence acceptance filter and publication projector keyed to the active, versioned retention/publication policy. If policy changes later, recompute/suppress public projection as required; do not rewrite past observations silently. Decide the treatment of pre-policy historical rows before export, including tombstone propagation and takedown handling.
6. Enable live-source smoke only with an explicit active approval or structured one-off approval, bounded request count, reviewed robots, expected retained fields and stop condition. Keep the default seven *capabilities* selected while unapproved sources have zero eligible fetch leases.

## Acceptance tests to add (not claims about today's suite)

| ID | Test scenario and required assertion |
| --- | --- |
| GATE-01 | With all seven capabilities selected and an unapproved manual seed queued, automatic robots refresh follows the chosen documented preflight rule; **claim is empty** and zero product requests are made. An unapproved auto-queued job behaves identically. |
| GATE-02 | A valid exact-scope approval permits only the matching canonical URL/method/platform/purpose after fresh robots allow and origin pacing. Adjacent path (`/item2` vs `/item`), query, subdomain, redirected host, wrong method and wrong platform fail. Directory scopes respect slash boundaries. |
| GATE-03 | A VPM lead matching an auto-queue rule but lacking source approval may become a queued job if chosen by design, yet never receives a lease. A source-approved but rule-unmatched lead remains pending review. Manually approved leads still need source approval under option B. |
| GATE-04 | Missing, stale, disallowing or unreachable robots never yields a lease, even with active source approval. A 404/410 robots result follows the RFC-specific missing-file behavior but cannot bypass source approval. Refresh requests obey the chosen preflight policy. |
| GATE-05 | Disable, expiry, source objection or scope narrowing atomically prevents new claims and rejects an in-flight fetching heartbeat and new result submission. The node's periodic heartbeat aborts egress within its documented interval; test an injected blocked fetch. Distinguish this from an instantaneous network-wide cancellation claim. |
| GATE-06 | Node credential revoke, URL suppression and auto-queue-rule disable retain their own scopes. Source approval disable stops both manual and rule-backed jobs matching that source; a neighboring approved source remains operable. |
| GATE-07 | Two coordinator processes racing to claim or refresh the same origin cannot exceed the origin lease/budget. Revoke during claim/submit uses SQLite transaction boundaries; no post-revocation new evidence is committed. |
| GATE-08 | A duplicate identical submission returns the recorded idempotent result without another version/event, including after later policy disable; a changed body/key for the same lease is rejected. The audit distinguishes “previously accepted” from “currently authorized.” |
| GATE-09 | A response with normalized facts, raw payload, creator prose and image derivative is retained only for explicitly allowed classes. Public export includes only publishable classes; unknown class is withheld. Revocation/public suppression does not silently imply either historical deletion or continued publication. |
| GATE-10 | Migration from an old local coordinator DB with seeded `source_rule_id NULL` jobs and rule-backed jobs creates **zero** active approvals. No existing job can claim after upgrade without deliberate review. No prototype DB data is silently imported. |
| GATE-11 | Operator route rejects absent/node/invalid token, malformed or wrong-version JSON, broad/ambiguous scope, expired approval and an attempted silent widening. An audit event exists for every approval/disable action. In-process and loopback HTTP validation agree. |
| GATE-12 | A small opt-in live test for one specifically reviewed endpoint records origin, exact URL, effective approval revision, robots snapshot ID, lease ID, retained classes and request count. It verifies no binary download, unexpected redirects or unapproved outbound leads. No fixture-only test is labeled proof of live compliance. |

The existing `tests/local_coordinator_protocol.test.ts`, `tests/operator_control_api.test.ts`, `tests/robots_refresh_service.test.ts`, `tests/node_lease_runner.test.ts` and live smoke scripts are natural test locations, but their current green status does **not** prove GATE-01–12. The first implementation slice after a decision should be the policy table/evaluator plus GATE-01, GATE-02, GATE-05 and GATE-10; then wire every boundary before enabling another live source.
