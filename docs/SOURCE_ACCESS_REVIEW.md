# Source access checkpoint (2026-09-27)

This is an engineering gate record, not legal advice. Driver selection is distinct from authorization to issue live requests or retain/publish fetched material. The new node defaults to all seven capabilities but receives no jobs until the local operator explicitly seeds them. Only the isolated, metadata-only VPM and GitHub smoke runs described below have been performed; no sustained source crawl has run.

The intended broader flow is discovery-driven: a node executing an assigned driver task reports provenance-bearing leads; the coordinator/Worker decides which become eligible jobs and controls leases, pacing, and stop rules. The current operator-seeded slice is a bootstrap, not the complete discovery model. Whether a seed itself constitutes source-access approval or an independent reviewed source profile is required remains a separate, unresolved policy choice. Neither a discovered lead nor an enabled driver is automatically permission to fetch.

**Current enforcement gap:** In the local coordinator, an operator `seed` makes a job eligible for lease after the robots gate even without a distinct source-access review record. The VPM lead auto-queue rule is scoped and auditable but does not encode a complete access/retention profile either. This is an explicit pre-production gate, not evidence that robots grants permission. The recommended decision is a separate, scoped, expiring operator source profile that both manual and rule-queued jobs must satisfy; the owner has not yet accepted that exact approval granularity.

The owner has since selected **hybrid lead review**: reviewed source rules may auto-queue matching leads; unfamiliar leads remain pending. The separate operator API supports authenticated, audited manual VPM-listing review and narrowly scoped, expiring VPM-listing auto-queue rules. It has no broad source-access/retention profile or other-driver promotion yet. Its rule creation and lead approval actions are operator judgments, not general legal findings; disabling a rule stops its future and in-flight rule-backed fetches but does not remove already retained evidence or separately seeded jobs. See [operator control API](OPERATOR_CONTROL_API.md).

**Jinxxy interpretation boundary:** The API clause is not limited to storefront editing: §23.2 says *all automated access* must use the official API unless written permission is obtained, and §8.2 separately addresses automated systems and systematic retrieval for directories/databases. Conversely, the API Jinxxy currently documents is the Creator API, with dashboard credentials and store-specific products, customers, licenses and orders. We have not found first-party documentation for a public cross-creator catalog endpoint; absence of documentation is not proof no such endpoint exists. The public marketplace and sitemap demonstrate discoverability by a human/browser, not a stated exception for this project's automated index. The remaining question for Jinxxy is how it intends third-party public catalog discovery to work, if at all. This is a first-party-policy interpretation to confirm, not a technical inference to settle by inspecting undocumented browser calls.

**Robots implementation checkpoint:** The legacy worker checks queued URLs, but direct driver fetches were not all mediated by that check. Its shared helper previously treated a network failure fetching `robots.txt` as allow-all; this now fails closed, matching [RFC 9309 §2.3.1.4](https://www.rfc-editor.org/rfc/rfc9309.html#section-2.3.1.4). The [parser package spike](ROBOTS_PACKAGE_SPIKE.md) replaces handwritten legacy rule matching and tests repeated groups and encoded paths. The local coordinator persists bounded per-origin robots snapshots, withholds claims until a fresh snapshot exists, checks exact URLs using the same strict parser, and rejects submissions after policy becomes disallowing. Its trusted `refresh-robots` command follows up to five HTTPS redirects, including across hosts, with a fresh pinned-DNS check at each hop; rules remain attached to the initial origin. `refresh-queued-robots [limit]` batches only already-seeded, nonblocked origins with a due job and missing/stale snapshot, using a SQLite refresh lease across processes. The `serve` process runs the same bounded batch on startup and every minute; this is not a source-authorization decision. Fixture and two-process checks passed; a narrow opt-in live VPM smoke verified compiled automatic startup refresh before node ingestion, while the earlier GitHub smoke used the explicit batch command. Standalone metadata requests now abort after a lease-bound heartbeat fails; this is bounded polling, not an instantaneous source-wide stop. This is **partial** centralization: crawl-delay, source-specific terms/retention policy, legacy direct-fetch coverage, and creator-wide cancellation remain open. The shared itch `/search` guard at legacy browse, seed, and node fetch boundaries is a narrow known-path stop, not a substitute for that work.
