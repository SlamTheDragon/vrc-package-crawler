# Local multi-process lease and idempotency spike (2026-09-27)

The local coordinator's claim, submit, suppression, and seed operations read state before writing it. The earlier in-process tests could not prove behavior across two SQLite connections/processes. [SQLite's transaction reference](https://sqlite.org/lang_transaction.html) explains that a default deferred transaction can begin with a read and fail when promoted to a writer after a concurrent change; `BEGIN IMMEDIATE` takes the write transaction before the read. [Bun's SQLite API](https://bun.com/docs/runtime/sqlite#transactions) exposes this as `transaction(...).immediate()`. This is local SQLite adapter behavior, not a claim that Cloudflare D1 has the same transaction semantics.

`src/worker/local_sqlite.ts` now uses immediate transactions for origin claims, result ingestion, suppression, and seed eligibility checks. The suppression check moved inside the seed transaction. A principal carries an opaque credential generation, and claim/submit recheck it within the transaction so a token rotated or revoked after initial authentication cannot act on a stale principal.

`bun run smoke:multi` compiles no code itself; run `bun run build:coordinator` first. It creates an isolated temporary SQLite file, starts two **separate compiled coordinator processes** against it, and sends 24 concurrent claim requests for two jobs on one origin. One lease is issued. Simultaneous submissions of that lease through the two processes yield one new result and one idempotent duplicate, with one persisted result/event. In a separate capability scope, an operator suppresses an already-leased URL through the CLI; submission to the other process returns 403 and the suppressed URL is not leased again. The smoke then deletes only its validated temporary directory. No external source is fetched.

This proves one bounded scenario, not G5 exit. Remaining evidence: sustained concurrent load, crash/restart and lease-expiry replay, WAL growth/checkpoints, operating-system process locks, origin fairness under many platforms, coordinator loss during an in-flight fetch, and a Worker/D1 implementation with its own consistency model. Even with `BEGIN IMMEDIATE`, SQLite documents that `SQLITE_BUSY` can still occur under contention; the adapter currently uses a 10-second busy timeout, but no retry policy or load-derived sizing has been validated. See [SQLite WAL concurrency and busy behavior](https://sqlite.org/wal.html).
