# VPM listing-template research (2026-09-27)

This is a source-format and implementation checkpoint, not a claim that VPM discovery is complete or that every listing host permits automated access. Primary references: [listing template](https://github.com/vrchat-community/template-package-listing), its [source.json](https://github.com/vrchat-community/template-package-listing/blob/main/source.json) and [workflow](https://github.com/vrchat-community/template-package-listing/blob/main/.github/workflows/build-listing.yml), the [builder's source model](https://github.com/vrchat-community/package-list-action/blob/main/PackageBuilder/ListingSource.cs) and [build code](https://github.com/vrchat-community/package-list-action/blob/main/PackageBuilder/Build.cs), [VCC listing guide](https://vcc.docs.vrchat.com/guides/create-listing/), [repo format](https://vcc.docs.vrchat.com/vpm/repos/), [package format](https://vcc.docs.vrchat.com/vpm/packages/), and the [published example listing](https://vrchat-community.github.io/template-package/index.json).

| Question / prior assumption | Observed reality | Decision for this implementation | Remaining risk or test |
| --- | --- | --- | --- |
| Is `source.json` a VPM package listing? | No. The template's source is a **recipe**: listing metadata, `githubRepos`, and `packages[].releases` ZIP URLs. A GitHub Action runs `BuildRepoListing`, which writes the installable `index.json`. | Treat the recipe's repository and ZIP references as *unverified discovery leads*, never as package/version evidence. The node now submits typed leads; the coordinator stores them as `pending_review`, and an operator may approve only a listing lead for a new crawl job. | Host access-policy decisions and automated, scoped lead traversal remain open. GitHub/ZIP leads are not automatically fetched. |
| Does a release ZIP filename or GitHub tag prove a VPM version? | The builder fetches each ZIP, extracts its `package.json`, derives name/version from that manifest, and adds the ZIP URL and SHA-256 before generating a listing. | Use a generated listing's embedded manifest as version evidence; do not infer version from a tag or filename, and do not replicate ZIP downloads merely to populate metadata. | For a repo without an accessible listing, a manifest-in-release API path needs separate access, bandwidth, and zero-binary review. |
| Can a listing contain multiple packages and versions? | Yes: `packages.{packageId}.versions.{version}` embeds full manifests; the published example includes `url` and `zipSHA256`. VCC says previously published versions should remain available. | The node submits a bounded batch of package observations with real version keys, dependency **ranges**, optional HTTPS download URL, and optional ZIP checksum. Bad entries yield a typed `partial_batch` with persisted diagnostics; no missing release is inferred to be deleted. | Current one-result limit is 100 packages, 100 versions per package, 100 diagnostics, and 240 KB serialized. Larger listings require paged/chunked evidence with lease-safe commit semantics. |
| Is the first manifest the latest release? | The format is a map; the builder separately applies VPM version ordering for its website. Map iteration order is not a release-ranking guarantee. | Do not label the first observed version as latest. Current title/author/summary choose the first nonempty field as provisional source display data. | Add VPM-compatible version comparison using a maintained library or clearly tested reference implementation before latest-version projections. Preserve prerelease behavior. |
| Is `packages[].name` a reliable package ID in the recipe? | The template example uses `name`, while the builder model has `PackageInfo.id`. In the current build path, only `releases` are read from these entries; neither label establishes the output package ID. | Do not promote either recipe label to canonical identity. | Confirm behavior against future builder revisions; this is a documented template/model drift, not proof that the listing is broken. |
| Can a package ID stand alone as a source identity? | The same ID may be referenced by more than one listing, with different metadata or release sets. | Source versions are keyed by listing URL plus package ID; future canonical linking may join them only through reversible evidence. | Repository URL moves, mirrors, claimed ownership, conflicts, and delisting need explicit models and replay tests. |
| Are the recipe and emitted listing identical in content? | No. Build code creates a `VRCRepoList` from package manifests; template description, `infoLink`, and banner are used on the website, not necessarily preserved in listing JSON. The published example confirms manifest-level URL/hash fields. | Keep listing/creator-page metadata as source-specific evidence; avoid assuming every recipe field survives publication. | Test real feeds from multiple generators, not just this template. |

The present code proves a narrow local slice: a generated-listing fixture passes `parseVpmRepository`, the same package ID in two listing jobs remains separate source evidence, and `source.json` yields typed discovery leads rather than package observations. An opt-in compiled node/coordinator smoke fetched the official published example listing and raw template recipe on 2026-09-27 into a temporary database: one `com.vrchat.demo-template` package with release `0.0.7` and a hash, plus four pending leads (one listing, one GitHub repository, two ZIP URLs). It did not fetch ZIP bytes. This does **not** establish source-policy clearance for arbitrary hosts, complete lead traversal, SemVer/reverse-DNS validation, a public release projection, or general live preproduction operation. Those remain G2–G5 work. The official builder downloads ZIP bytes because it publishes a repository; our catalog's zero-binary metadata boundary is different.
