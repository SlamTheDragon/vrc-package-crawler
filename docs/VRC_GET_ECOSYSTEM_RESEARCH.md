# VPM ecosystem beyond a listing (2026-09-27)

This is a compatibility research note, not a claim that the crawler is a VPM client or that all public feeds are approved for crawling. [vrc-get](https://github.com/vrc-get/vrc-get) contains the `vrc-get` CLI, `vrc-get-gui` (ALCOM), and the separate `vrc-get-vpm` library. The [CLI's documented commands](https://github.com/vrc-get/vrc-get/blob/master/README.md) distinguish local repository subscriptions and search from project install, resolve, upgrade, and remove operations. ALCOM is a [Creator Companion alternative](https://github.com/vrc-get/vrc-get/blob/master/vrc-get-gui/README.md), **not** a community repository listing to ingest.

| Prior thought / tempting shortcut | Observed ecosystem reality | Catalog decision and gate impact |
| --- | --- | --- |
| Any VPM-looking JSON is a repository. | [VCC repositories](https://vcc.docs.vrchat.com/vpm/repos/) are JSON listings with `packages.{id}.versions.{version}` manifests. The [Resolver](https://vcc.docs.vrchat.com/vpm/resolver/) compares a project's `Packages/vpm-manifest.json` with its Packages folder. VCC also accepts local user-package folders. | G3 must explicitly distinguish published listing, individual `package.json`, listing build recipe, local project manifest, and user-package folder. The latter two are not public discovery feeds. Do not probe arbitrary repository roots for `vpm-manifest.json`. |
| A VPM package ID implies a single globally canonical repository or available release. | The [vrc-get CLI](https://github.com/vrc-get/vrc-get/blob/master/README.md) adds/removes installed repositories locally. VCC lets users enable/disable subscriptions and choose selected repos per project; private repos can require request headers. [VCC guide](https://vcc.docs.vrchat.com/guides/community-repositories/). | Preserve listing URL, declared repo `id`, package ID, and release evidence separately. A package's appearance in one listing does not prove that another client has subscribed to it, can fetch it, or is authorized to access it. Public catalog links must identify the upstream repository, not claim universal installability. G2/G4. |
| We can choose the first version or implement an approximate resolver. | [vrc-get's repository parser](https://raw.githubusercontent.com/vrc-get/vrc-get/master/vrc-get-vpm/src/repository/remote.rs) stores versions in a map and its latest selector excludes yanked releases by default. [VCC package docs](https://vcc.docs.vrchat.com/vpm/packages/) describe prerelease opt-in and dependency ranges; [vrc-get's own issue](https://github.com/vrc-get/vrc-get/issues/1696) documents a resolver difference from VCC for an OR range. | Retain exact version and dependency-range strings as observed; no map-order latest, fabricated default version, homegrown compatibility or installability promise. Research yanked/pre-release semantics and use a maintained compatible version library before a latest/compatible projection. G4. |
| Rejecting a whole listing on one bad release is equivalent to VPM clients. | The [vrc-get remote parser](https://raw.githubusercontent.com/vrc-get/vrc-get/master/vrc-get-vpm/src/repository/remote.rs) logs a malformed release manifest and skips that version rather than losing every other version. It also supplies missing repository URL/ID from the fetch URL for its local representation, and supports conditional ETag fetches. | Current `parseVpmRepository` rejects an entire listing on one malformed entry. This is safe against silent partial publication but causes avoidable data loss; design per-entry quarantine with diagnostics and atomic snapshot semantics before changing it. A client's fallback ID is not a publisher assertion. G3/G4. |
| A package's download URL should be crawled to verify the catalog. | [VCC package docs](https://vcc.docs.vrchat.com/vpm/packages/) say repository manifests can carry a ZIP URL and checksum; the catalog's zero-binary boundary is narrower than an installer/publisher's. | Store bounded metadata and source provenance; never fetch ZIPs to fill catalog fields. A URL/checksum is evidence from a listing, not evidence that the binary is still reachable or safe. G3/G5. |

## Code-path consequences

- `src/node/observation_adapter.ts` accepts listing manifests and build recipes into bounded protocol payloads. A malformed release now yields a `partial_batch` with a bounded issue code; valid manifests remain separately observed. The coordinator persists those diagnostics and an `incomplete_listing` event. Each source version has a `complete` marker. Its private `vpm-evidence` read model selects the latest **complete** version per source item and excludes suppressed listings, so a missing release in a partial response is not interpreted as deletion. This read model is not an installable index or accepted public catalog. A listing with more than 100 packages still fails; an oversized package version map is marked invalid. The parser does not yet carry declared repository ID, yanked status, or a VPM-compatible latest selector. These remain G3/G4 gaps, not reasons to fabricate a release.
- `src/shared/node_protocol.ts` preserves dependency ranges as strings, which matches the catalog's evidence role. Avoid a resolver until the product scope explicitly calls for project-specific install advice.
