# Operator control API and hybrid lead review

**Owner decision (2026-09-28):** a discovered lead matching a reviewed source rule may become a coordinator job automatically. Unknown hosts, paths, or lead kinds stay pending for review. A node still needs a coordinator lease before fetching; selecting all seven driver capabilities is not blanket authorization.

The control API is separate from `/v1/node/*`. The local coordinator currently binds to `127.0.0.1`; it accepts operator requests only when `COORDINATOR_OPERATOR_TOKEN` is configured as a 64-character hex token generated from 32 random bytes. Node credentials do not authorize operator routes. The token is never passed to standalone nodes by the local smoke. A future dashboard can call this versioned API through a same-origin Worker/adjacent control application; no dashboard, account system, remote TLS, or Cloudflare deployment exists yet.

| Route | Current behavior | Still needed for the accepted hybrid |
| --- | --- | --- |
| `GET /v1/operator/leads?status=pending_review&limit=100&cursor=...` | Lists bounded pending, approved, or rejected leads after operator authentication, ordered by first-seen time and lead key. Returns `nextCursor` until the selected status is exhausted; the cursor is bound to that status | Snapshot-consistent browsing under concurrent changes and richer provenance/review evidence |
| `POST /v1/operator/leads/{leadKey}/approve` | Validates JSON `{schemaVersion:1,reason,minDelayMs?}`, seeds only a VPM listing lead, and records an audit action | General safe lead-to-job mappings and source-profile check |
| `POST /v1/operator/leads/{leadKey}/reject` | Validates JSON `{schemaVersion:1,reason}`, rejects a pending lead, and records an audit action | Explicit reconsideration/reversal workflow |
| `GET /v1/operator/autoqueue-rules?limit=100&cursor=...` | Lists bounded rules, including disabled ones, in reverse creation order; returns `nextCursor` until exhausted | Source-wide access/retention profile and snapshot-consistent browsing under concurrent changes |
| `POST /v1/operator/autoqueue-rules` | Creates an expiring, audited rule for a VPM listing lead kind, canonical HTTPS origin, exact path or directory prefix, minimum delay, review reference and reason. No default rules are installed. | Other lead kinds/drivers, source-wide terms/retention fields, revision workflow, and review evidence verification |
| `POST /v1/operator/autoqueue-rules/{ruleId}/disable` | Audits disablement, clears active rule-backed leases, and prevents subsequent claims, fetching heartbeats, and result submission for those jobs | Source-wide stop, creator-wide delisting, and treatment of already retained/published evidence |

| Automatic lead promotion | New VPM listing leads matching an active, unexpired rule become jobs in the same submission transaction. Unmatched paths/hosts, queried URLs, unsupported kinds and rejected leads remain unpromoted. | Reconcile leads that were pending before rule creation; general typed lead-to-job mappings and complete source policy at every fetch path |

The operator handler reuses the bounded JSON request reader and validates the same request whether called in-process or through loopback HTTP. Both node and operator handlers pass browser-target builds, but neither is yet a deployed Worker application. The compiled smoke checks that the operator token works and a node token does not. `operator_actions` records manual lead decisions; `operator_rule_actions` records rule creation, disablement, and failed automatic promotions. The CLI remains an explicit local control path; it is not a substitute for the future dashboard identity and authorization model.

The `leads [status] [limit] [cursor]` CLI uses the same keyset pagination and prints `{leads,nextCursor}`. A cursor is opaque, bounded, validated and tied to the selected status; malformed or cross-status cursors fail. This avoids hiding leads beyond the first 100, but it is not a frozen snapshot: newly discovered or reclassified leads may appear or disappear while an operator pages through a changing status set.

The auto-queue-rule list also uses a bounded, opaque keyset cursor and returns `{rules,nextCursor}`. Rules created while paging can change what a later page contains; neither list is a frozen snapshot.

**Source-profile boundary is local and partial.** Both manual and auto-queued jobs need a matching active profile before automatic/explicit robots refresh or a node lease. The lease binds the profile ID; fetching heartbeats and new submissions recheck it, and the profile's delay raises origin pacing. `retainClasses` reaches the node through the versioned job payload; unapproved creator prose is stripped and independently rejected if submitted. New evidence records the profile ID. This does not approve any particular source, enforce publication classes in a public catalog, cover legacy direct drivers, or provide a complete delisting/retention workflow. The profile list returns `{profiles,nextCursor}`. See `docs/decisions/current/access/SOURCE_ACCESS_GATE_DESIGN.md`.

The initial profile manager rejects overlapping active path scopes for the same platform, origin and purpose. This avoids silently falling back to a broader grant when a narrow grant is disabled. A later revision workflow can explicitly replace or narrow a profile with a reviewed transition; none is implemented yet.

An exact path rule such as `/index.json` matches only that path with no query. A scope ending in `/` matches paths in that directory. Rules are initially limited to `vpm_listing`; repository and ZIP leads stay pending. Disabling or expiring a rule stops its future and in-flight fetch authority, **but does not erase existing evidence or retroactively cancel separately operator-seeded jobs**. That broader source-access/retention stop remains a distinct open gate. Existing pending leads are not auto-reconciled when a new rule is created; an operator may review them individually until a bounded reconciliation action exists.

Source-access profiles are separate from these auto-queue rules. Their optional `exactQuery` is an ASCII `key=value` sequence (for example `page=1`) attached to one exact `pathScope`; it never acts as a wildcard or extends a directory grant. A canonical percent-encoded UTF-8 path can be reviewed as an exact path, but encoded ASCII and encoded directory scopes are rejected. Existing profiles without `exactQuery` continue to match only query-free targets. Creating a profile is an operator review action, not evidence that a particular source permits crawling.

The node result schema also accepts `creator_profile`, `publisher_site`, and `storefront_product` discovery leads, optionally anchored to a `discoveredFromItemKey` on a multi-item source page. The operator list exposes that anchor as `discovered_from_item_key`; older leads have `null`. These kinds remain pending and cannot be approved as VPM jobs or matched by the present VPM-only auto-queue rules. Recording the anchor does not authorize following the link or establish author ownership or product equivalence.

A reviewed auto-queue rule must not be reduced to `robots.txt` permission or presented as a full legal/source-access profile. The future full profile needs allowed endpoint/method, discovery role, retained and publishable fields, rate floor, stop condition, review evidence, actor, revision and expiry. A newly found URL is a lead, not accepted catalog fact. Neither a node nor a dashboard should bypass the coordinator's lease and policy checks.
