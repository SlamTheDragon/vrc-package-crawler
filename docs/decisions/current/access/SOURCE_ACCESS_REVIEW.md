# Source access checkpoint (2026-09-27)

This is an engineering gate record, not legal advice. Driver selection is distinct from authorization to issue live requests or retain/publish fetched material. The new node defaults to all seven capabilities, but a seed now only queues a job; a separate active scoped source profile and robots allow are required before refresh/lease. Earlier isolated VPM and GitHub smokes predated this gate. Revised GitHub and VPM template smokes passed on 2026-09-28 with exact-path profiles, normalized-facts-only retention, and no publication classes. No sustained source crawl has run.

The intended broader flow is discovery-driven: a node executing an assigned driver task reports provenance-bearing leads; the coordinator/Worker decides which become eligible jobs and controls leases, pacing, and stop rules. The current operator-seeded slice is a bootstrap, not the complete discovery model. The owner chose a separate scoped source-access profile for both manual and auto-queued jobs; neither a discovered lead nor an enabled driver is automatically permission to fetch.

**Current enforcement boundary and gaps:** The local coordinator now requires an active scoped profile before robots refresh, lease claim, fetching heartbeat and new submission. `seed` and a VPM lead auto-queue rule create or promote jobs but do not grant fetch access. The profile captures reviewed endpoint, purpose, cadence, expiry, and retention/publication classes; its creation is an operator judgment, not a legal finding. Legacy direct drivers, source-specific review evidence, historical/public projection, retention duration and delisting still lack equivalent end-to-end enforcement. Robots allowance alone never grants permission.

The owner also selected **hybrid lead review**: reviewed source rules may auto-queue matching leads; unfamiliar leads remain pending. The separate operator API supports authenticated, audited manual VPM-listing review, narrowly scoped expiring VPM-listing auto-queue rules, and source-access profile create/list/disable. It does not yet promote other-driver leads. Rule creation and lead approval are operator judgments, not general legal findings; disabling a rule stops its future and in-flight rule-backed fetches but does not remove already retained evidence or separately seeded jobs. Disabling a source profile stops new local-coordinator leases in its scope and invalidates its active leases, but does not yet remove or suppress retained/public historical data. See [operator control API](../api/OPERATOR_CONTROL_API.md).

### GitHub one-request engineering scope (2026-09-28)

Review reference `docs/decisions/current/access/SOURCE_ACCESS_REVIEW.md#github-one-request-engineering-scope-2026-09-28` applies **only** to an opt-in local test of `GET https://api.github.com/repos/vrc-get/vrc-get`, with no authentication, search, README, release, archive, or follow-on requests. GitHub's current [Get a repository reference](https://docs.github.com/en/rest/repos/repos?apiVersion=2026-03-10#get-a-repository) says public resources can be requested without authentication; its [API version reference](https://docs.github.com/en/rest/about-the-rest-api/api-versions) lists `2026-03-10`, and its [rate-limit reference](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api) gives 60 unauthenticated requests/hour per source IP with response headers as authoritative. The local script's one metadata request, 60-second origin floor, bounded observation, `normalized_facts` retention, and empty publication classes are the engineering limits for this check. Runtime robots and response status remain decisive. This is **not** a legal opinion, a permission for broad repository harvesting, or approval to publish the description; GitHub's [Terms](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service) and [Acceptable Use Policies](https://docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies) still apply. If the runtime returns a denial/challenge/rate limit, stop without retrying this test automatically.

Outcome: the default sandbox could not connect for robots (`ECONNREFUSED`), so it made no product request. The same reviewed test passed when run with network access: robots preflight succeeded, one compiled standalone node returned `changed`, and the isolated coordinator persisted `github:590790034` with the expected source link. The later one-time pacing regression retest also passed, including the added stored-profile-attribution and prose-minimization assertions. The temporary databases were removed by the script. This proves bounded local profile-gated requests, not a sustained crawl or a source-wide permission finding.

### VPM two-template engineering scope (2026-09-28)

Review reference `docs/decisions/current/access/SOURCE_ACCESS_REVIEW.md#vpm-two-template-engineering-scope-2026-09-28` applies only to one opt-in local test of these two exact `GET` URLs: `https://vrchat-community.github.io/template-package/index.json` and `https://raw.githubusercontent.com/vrchat-community/template-package-listing/main/source.json`. They belong to **different** public VRChat-community template repositories. The first is the [Package Template](https://github.com/vrchat-community/template-package)'s published example listing; the second is the [Package Listing Template](https://github.com/vrchat-community/template-package-listing)'s build recipe. The latter is not the recipe that generated the former. VRChat's [VPM repository format](https://vcc.docs.vrchat.com/vpm/repos/) and [listing guide](https://vcc.docs.vrchat.com/guides/create-listing/) document public JSON listings consumed by VPM clients, but do not grant broad collection or redistribution rights. Runtime robots must permit both origins independently. The script creates separate exact-path, `discovery`-purpose, 30-minute profiles, retains only `normalized_facts`, publishes no evidence classes, runs two compiled nodes once, and never follows the recipe's repository or ZIP leads. A denial, challenge, malformed response, or rate limit ends this check; no automatic retry or wider URL scope is authorized. This is an engineering test boundary, not legal advice or blanket approval of GitHub Pages, raw GitHub, or third-party listings.

Outcome: the revised compiled smoke passed. The temporary coordinator recorded `com.vrchat.demo-template` release `0.0.7` with a ZIP hash as metadata, but fetched no ZIP; it stored four recipe-derived leads as `pending_review`. The listing version and all four leads had source-profile attribution, and the retained listing summary was empty under the `normalized_facts`-only profile. Two distinct node PIDs completed through the loopback API. The isolated database was removed by the script. This proves two narrow real-source paths and protocol wiring, not recipe-to-output equivalence, automatic traversal, sustained ingestion, or general permission.

### One-time pacing regression retest scope (2026-09-28)

After the local coordinator began counting robots preflight against the same origin pacing floor as product fetches, one further run of each exact GitHub and two-template VPM smoke above is allowed as an engineering regression check. The URLs, methods, retain/publish classes, temporary storage, no-ZIP/no-follow-on limit, and robots/denial stop conditions are unchanged. The harnesses now wait for each persisted `next_allowed_at` before node claims; GitHub's reviewed 60-second floor applies after its robots request. This is not authorization for a recurring schedule or any additional source.

Outcome: both one-time regression retests passed. The VPM test again recorded one release and four pending leads with source-profile attribution and omitted prose after the two origin floors elapsed. The GitHub test waited the 60-second floor and then recorded `github:590790034`; its added assertion confirmed the stored profile ID and empty summary. No public projection or ZIP request occurred. This retest scope is spent.

This matrix deliberately does not label every selected driver “permitted.” The local protocol and fixture tests may advance while source-specific decisions are pending. The standalone node's [pinned HTTPS metadata transport](NODE_FETCH_SAFETY.md) blocks obvious private-network egress and redirects, but is not an access license. A first live-development run should record the approved endpoint list, request policy, retention/publication rule, and stop condition for each platform or origin before seeding its jobs.

**Jinxxy interpretation boundary:** The API clause is not limited to storefront editing: §23.2 says *all automated access* must use the official API unless written permission is obtained, and §8.2 separately addresses automated systems and systematic retrieval for directories/databases. Conversely, the API Jinxxy currently documents is the Creator API, with dashboard credentials and store-specific products, customers, licenses and orders. We have not found first-party documentation for a public cross-creator catalog endpoint; absence of documentation is not proof no such endpoint exists. The public marketplace and sitemap demonstrate discoverability by a human/browser, not a stated exception for this project's automated index. The remaining question for Jinxxy is how it intends third-party public catalog discovery to work, if at all. This is a first-party-policy interpretation to confirm, not a technical inference to settle by inspecting undocumented browser calls.

**Robots implementation checkpoint:** The legacy worker checks queued URLs, but direct driver fetches are not all mediated by the new coordinator. Its shared helper now fails closed on a network failure fetching `robots.txt`, matching [RFC 9309 §2.3.1.4](https://www.rfc-editor.org/rfc/rfc9309.html#section-2.3.1.4). The [parser package spike](../../../research/spikes/ROBOTS_PACKAGE_SPIKE.md) replaces handwritten legacy rule matching and tests repeated groups and encoded paths. The local coordinator persists bounded per-origin robots snapshots, withholds claims until a fresh snapshot exists, checks exact URLs using the strict parser, and rejects submissions after policy becomes disallowing. Its trusted refresh follows up to five HTTPS redirects with fresh pinned-DNS checks per hop; rules remain attached to the initial origin. Both explicit and queued robots refresh now require a due job matching a separate active source profile; an unapproved seed cannot trigger automatic robots egress. SQLite refresh leases coordinate processes, and `serve` runs a bounded pass on startup and every minute. Fixture and two-process checks passed. Revised exact-path GitHub and two-origin VPM smokes passed through this gate. Standalone metadata requests abort after a lease-bound heartbeat fails; this is bounded polling, not instantaneous source-wide stop. Centralization remains **partial**: source-specific terms/retention, legacy direct-fetch coverage, historical/publication handling and creator-wide cancellation remain open. The shared itch `/search` guard at legacy browse, seed and node fetch boundaries is a narrow known-path stop, not a substitute for those tasks.
